## Opus 확인
- 브리프에 없던 결정이 인계에 빠짐없이 있는가: 아니오. 인계에는 상태 화면 문구만 있다. 아래는 diff에서 찾아 DECISIONS에 적었다. 성공·404 뒤 종목 목록 전체를 OOB로 다시 그림(브리프는 "그 종목 조각"), 별칭 1~100자이고 다듬지 않음, 주기 선택지 글자에서 시각을 뺌, `clamp_depth`로 깊이 3·4를 2로 보임. 모두 되돌리기 쉬운 작은 것이라 반려하지 않는다.
- 테스트 기대값을 바꾸거나 빼서 통과시키지 않았는가: 예. 기존 시험 12개는 제약대로 고쳤다. 기본값을 확인하는 시험(`page.min_magnitude`, 타임라인 문구)은 새 값으로 바꿨고, 나머지는 시험 준비에서 옛 값(daily·6)을 직접 써서 원래 시나리오를 지켰다. 단언을 지운 것은 없다.
- 제약과 프로젝트 규칙을 지켰는가: 예. 손님에게는 × 버튼 없이 칩만 보이고, 지우기 POST는 기존 guard를 거친다(허용 목록에 넣지 않았다). 제품 기본값을 우회하지 않았고 `docs/`도 고치지 않았다.
- 인계가 실제 변경과 맞는가: 대체로 맞다. 다만 "범위 밖: 없음"은 틀렸다(`web.rs`). format:check 줄에는 숫자가 없었다.

## 반영한 것 (통과일 때)
- 영구 문서: DECISIONS 1장의 "17단계 tree-screen 상태 화면 문구"에 문구와 근거를 붙였고, "17단계 tree-screen 구현 세부" 줄(①~⑤)을 더했다. STATE에 tree-screen 통과를 넣고 다음 할 일을 갱신했다. SPEC FR-3의 옛 "관련도·영향도 보임"에 17단계 변경을 표시했고, FR-5 기준에 17단계 기본 6·5를 표시했다. README의 타임라인 기본 기준(6·6 → 6·5) 두 곳과 종목 줄(실적·별칭)이 옛 내용이라 리뷰가 고쳤다.
- 다음 브리프 확인: 인계 "다음 작업에 영향"은 설정 문구뿐이라 고칠 것이 없다. `eval-merge`·`topic-input`의 "알려진 함정"에 기본값 변경(영향도 5·weekly)을 적었다. 경계값은 기본값에 기대지 말고 설정으로 직접 써야 한다.
