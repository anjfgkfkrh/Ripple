원칙: 원인을 찾기 전에는 고치지 않는다. 증상만 덮는 수정은 실패로 본다. 간단해 보이는 버그도, 급할 때도 같다.

## 1. 원인 찾기 (고치기 전에 반드시)

- 오류 메시지·경고·스택을 끝까지 읽는다(파일:줄, 오류 코드).
- 다시 일으킨다. 매번 나는지, 어떤 단계에서 나는지. 다시 일으킬 수 없으면 자료를 더 모은다. 추측하지 않는다. 간헐 실패는 되풀이 실행으로 재현한다(예: `pnpm exec playwright test <파일> --repeat-each=10`).
- 최근 변경을 본다: `git diff`, `git log -5 --stat`, 의존성·설정·환경 차이(로컬 vs Docker, `.env` 키 있음/없음).
- 경계가 여러 곳이면 경계마다 들어가고 나오는 값을 한 번 찍어 어디서 깨지는지부터 찾는다. 이 프로젝트의 경계: web ↔ worker 내부 API ↔ DB, 수집 → 종목 연결 → Jev 평가 → 타임라인, 정기 작업 계획 → 실행, 컨테이너 ↔ 호스트.
- 잘못된 값이 어디서 왔는지 호출을 거꾸로 따라가 처음 생긴 곳을 찾는다. 고칠 곳은 증상이 아니라 그곳이다.

## 2. 비교

- 같은 코드베이스에서 잘 되는 비슷한 코드를 찾아 다른 점을 모두 적는다. "상관없겠지"로 지우지 않는다.
- 라이브러리 동작이 의심되면 공식 문서와 실제 소스(Rust 크레이트는 `rust/`의 `cargo` 소스 캐시나 docs.rs, TS 도구는 `node_modules/`)를 끝까지 읽는다.

## 3. 가설 하나씩

- "X 때문이다, 근거는 Y"를 하나만 세우고 가장 작은 변경으로 확인한다. 한 번에 하나만 바꾼다.
- 틀렸으면 그 변경을 되돌리고 새 가설을 세운다. 수정 위에 수정을 쌓지 않는다.
- 모르면 모른다고 말한다.

## 4. 고치기

- 먼저 실패하는 테스트를 만든다(가능하면 단위 테스트, 화면이면 E2E). 고치기 전에 실패하는 것을 본다.
- 원인 하나만 고친다. 하는 김에 하는 정리·리팩터링은 섞지 않는다.
- 고친 뒤 그 테스트, 원래 증상, 전체 검사(`/check`)를 본다. 완료라고 말하기 전에는 `before-done`.

## 5. 세 번 고쳐도 안 되면 멈춘다

고칠 때마다 다른 곳에서 새 문제가 나오거나 고치려면 큰 구조 변경이 필요하면, 가설이 틀린 게 아니라 구조 문제다. 더 고치지 말고 알아낸 것과 선택지(A/B, 장단점, 추천)를 사용자에게 보고하고 묻는다. 구조를 바꾸는 것은 사용자 결정이다(CLAUDE.md).

## 6. 원인이 없다고 결론 내리기 전에

대부분은 조사가 덜 된 것이다. 정말 환경·시간·외부 서비스 탓이면, 무엇을 조사했는지 적고 알맞은 처리(재시도, 시간 제한, 실패 기록·표시)와 다음에 볼 수 있는 로그를 더한다. 한 소스가 실패해도 나머지 수집은 계속 돌아야 한다(CLAUDE.md 아키텍처 원칙).
