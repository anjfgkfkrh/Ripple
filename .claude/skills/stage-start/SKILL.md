사용자가 새 단계를 시작하자고 했을 때만 쓴다. 그 요청이 이전 단계를 커밋해도 된다는 허락이다(DEVELOPMENT.md 3장). 푸시는 하지 않는다.

## 1. 이전 단계 정리

- DECISIONS.md 1장에서 이전 단계의 "— 구현 중 정함" 줄을 "— 구현 중 정함, 보고 후 이의 없음"으로 바꾼다(사용자가 보고를 받고 이의 없이 다음으로 갔으므로). 이의가 있었던 줄은 그 답대로 고친다.
- DEVELOPMENT.md 1장·2장을 지금 상태로 고친다. 끝난 단계의 자세한 기록은 DECISIONS.md 3장 맨 위로 보낸다.

## 2. 커밋

1. `git status --short`로 바뀐 파일을 본다. 커밋할 파일만 이름으로 `git add` 한다(`git add -A`·`git add .`는 쓰지 않는다). 모르는 파일이 있으면 멈추고 묻는다.
2. `node scripts/check-secrets.mjs` — 종료 코드가 0이 아니면 멈추고 찾은 곳을 보고한다(값은 출력되지 않는다).
3. main에 커밋한다. 메시지는 한국어로 첫 줄 "N단계: 요약", 본문에 주요 변경, 끝에 시스템이 알려 준 Co-Authored-By 줄. `.env`라는 글자가 메시지에 들어가면 Bash hook이 막으므로 메시지를 파일로 써서 `git commit -F <파일>`로 넘긴다.
4. `git log -1 --stat`으로 확인한다.

## 3. 새 단계 질문

- SPEC.md 10장에서 그 단계 줄(내용·완료 기준)을 읽고, 그 기능에 관련된 장만 읽는다. 13장에서 이 단계에 걸리는 D-xx를 찾는다.
- 코드는 DEVELOPMENT.md 8장 코드 지도에서 시작한다. 같은 기능의 지난 결정은 DECISIONS.md 1장에서 찾아 읽는다(`grep -n`).
- 질문은 한 번에 모아 묻는다(CLAUDE.md "결정은 내가 한다"): 항목마다 상황, 선택지 A/B와 장단점, 추천에 "(추천)". 작은 항목은 표 하나로 묶는다. 돈이 드는 확인이 필요하면 예상 비용도 함께 묻는다.
- 보낸 뒤 DEVELOPMENT.md 1장에 "N단계: 질문 보냄, 답 대기"와 질문 요약을 적는다(세션이 끊겨도 이어 갈 수 있게).

## 4. 답을 받으면

DECISIONS.md 1장에 먼저 적고(SPEC 13장 상태도 "결정됨"으로, 기능이 바뀌면 SPEC 본문도) 구현을 시작한다.
